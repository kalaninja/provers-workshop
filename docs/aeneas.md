# Aeneas lane

[Aeneas](https://github.com/AeneasVerif/aeneas) verifies Rust by *translation*:
[Charon](https://github.com/AeneasVerif/charon) extracts the crate to an LLBC
model, Aeneas translates that to a pure functional model in Lean 4, and the
contracts are hand-written Lean proved against the [Aeneas Lean
library](https://github.com/AeneasVerif/aeneas/tree/main/backends/lean) (over
mathlib). It is the first *interactive* prover in the roadmap and the only lane
whose specifications live entirely outside the Rust source. See
[provers.md](provers.md) for where it sits in the comparison; this is the full
lane report.

## What is wired

A full `ticketing-aeneas` program crate over `ticketing-interface` - a port of
the `ticketing-creusot` reference program with the whole spec layer moved out of
the source: trusted `instructions/` shells + dispatcher + `entrypoint!` around
the `flows/` cores and the `domain/` accounting, building a behavior-identical
`ticketing_aeneas.so`. The generated client's Mollusk suite passes against it -
the same 7 tests as the other lanes (`just solana test-client-rust ticketing
aeneas`).

- **No in-Rust verification surface.** Aeneas proves from the outside, so the
  crate carries no spec attributes, no `cfg(aeneas)` (absent from the workspace
  `check-cfg`), and no verifier dependency. It compiles as ordinary Rust on host
  and SBF.
- **Extraction-first control flow.** The extracted cores (`flows/`,
  `domain::event`) use explicit `if`/`match` instead of `?`: each `?` extracts
  through the `Try`/`ControlFlow` trait machinery and buries the Lean model in
  `branch`/`from_residual` scaffolding that every proof would have to simp away.
  The trusted shells (never extracted) keep ordinary `?`.
- **The extraction pipeline** (`scripts/aeneas/verify.sh`): `charon cargo
  --preset=aeneas` -> `.llbc` -> `aeneas -backend lean` -> `verif/ticketing_aeneas`.
  `[package.metadata.charon]` `start_from = ["crate::flows"]` scopes emission to
  the decision cores (the `instructions/`/entrypoint shells are never extracted),
  and `opaque` abstracts `domain::glue` and the wire types `Event`/`Ticket`.
- **Committed Lean, re-checked by `just aeneas replay`.** `TicketingAeneas.lean`
  is the Aeneas-generated model (regenerated by `verify`, never hand-edited);
  `TicketingAeneasProofs.lean` is the hand-written proofs. Both are committed and
  checked by compiling with `lean` against the image's prebuilt oleans (not `lake
  build`, which re-clones mathlib each run - see the note below).

## What is proved

The pure decision cores run on `u64` and enums that Aeneas models precisely, so
the arithmetic Flux had to *trust* is *proved* here. All six cores carry
machine-checked Lean contracts (`⦃ ⦄` total-correctness triples), mirroring the
Creusot reference lane's coverage:

- **`payment_for`** - `payment = quantity * price` with **no overflow**, for
  `quantity <= capacity`. The nonlinear `quantity * price <= capacity * price <=
  u64::MAX` step is proved from the event invariant by mathlib monotonicity
  (`Nat.mul_le_mul_right`). *Flux trusts this as a `mul_le_mono` lemma; Verus
  discharges it with one `by (nonlinear_arith)`; Aeneas proves it in Lean.*
- **`create_event`** - `Ok` yields an initial event **satisfying the invariant**
  (the invariant's base case); the error occurs **exactly when** `capacity *
  price` overflows `u64` (the `Ok`/`Err` discriminant, via a modeled
  `checked_mul`). *Flux drops this characterization.*
- **`record_sale`** - preserves the event invariant (so `sold <= capacity` is
  maintained - **no overselling**), changes only `sold`, returns the **exact
  positive clamp** `min(requested, capacity - sold)`, grows `sold` by exactly
  that quantity, succeeds exactly when sales are open with headroom left (on
  error the event is unchanged and either sales were closed or `sold =
  capacity`). The no-oversell guard rides `set_sold`'s trusted precondition
  (`v <= capacity`), discharged from the clamp.
- **`close_sales`** and **`close_event`** - preserve the invariant, change only
  `status` (`open -> closed`), authenticate the organizer (`close_event`), and on
  error leave the event unchanged (the exact `Ok <=> organizer ∧ open`
  discriminant).
- **`purchase`** (ticket_buy) - the **end-to-end composition**: invariant
  preserved, only `sold` changes and grows by exactly the ticket's clamped
  quantity, the organizer is authenticated, the ticket pins the
  event/buyer/payment/bump/slots (the analog of Creusot's `is_initial`), the
  payment is exactly `quantity * price`, and on error the event is unchanged.

## Trusted surface

Because `Event`/`Ticket`/`Address`/`NonZeroU64` are opaque in the extracted model
(the wire structs have a recursive `AccountHeader` header and padding; `NonZero`
has no Lean model), the field-level `domain::glue` becomes uninterpreted axioms
that the proofs equip with trusted `@[step]`/`@[simp]` specs - the declared TCB,
the analog of Flux's `#[extern_spec]`s and Creusot's `#[trusted]` shims:

- logical projections of the opaque `Event` (organizer/slots/capacity/price/sold/
  bump/closed) and `Ticket` (event/buyer/paid/quantity/bump/slots), plus the
  `Event.inv` predicate;
- accessor specs (`get_capacity`/`get_price`/`get_sold`/`is_open`/`organizer_eq`);
- setter specs with frame + update, incl. `set_sold`'s load-bearing `v <=
  capacity` no-oversell precondition, and `set_status_closed`;
- constructor specs: `event_new` and `ticket_new` pin every projection of the
  fresh value (the analog of Creusot's `is_initial` postconditions);
- the `NonZeroU64 <-> u64` bridges (`nz_get`/`nz_from`, incl. `nz_from`'s
  identity-on-positives spec backing its dead `None` arm) and `Address`
  `is_set`/eq.

Everything else - the clamp, the no-underflow/no-overflow arithmetic, the status
step, the invariant preservation - is proved, not trusted. This is a *smaller*
arithmetic trusted surface than Flux (which trusts the nonlinear `mul_*` lemmas),
at the cost of the largest proof-authoring effort of the roster.

## Tooling notes (deviations from the Creusot/Kani template)

- **`--sysroot default` for the cdylib.** The crate is a `cdylib` (for
  `cargo build-sbf`), and Charon's default MIR-only sysroot cannot *link* one on
  the host (its std libs carry MIR, not compiled objects). The normal distributed
  sysroot links fine, and std/core stay opaque either way (Aeneas maps
  `checked_mul`/`*` via its builtin table). Charon's build is isolated in its own
  `CARGO_TARGET_DIR` since that sysroot's std differs from the stable
  rust-tooling toolchain's.
- **`lean`, not `lake build`.** Lake re-resolves and re-clones mathlib from the
  network every run; `scripts/aeneas/lean-check.sh` points `LEAN_PATH` at the
  image's prebuilt Aeneas + mathlib oleans instead - hermetic, no network.
- **Heaviest image, slowest lane.** OCaml-built Charon+Aeneas + a Lean toolchain
  + the mathlib tree; a full `verify` rebuilds Charon's MIR sysroot. `replay`
  (the pre-push gate) is the cheap re-check of the committed Lean.
